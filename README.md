# AI-Powered Application Incident & Support Assistant

An incident-response assistant that ingests application errors, classifies them, retrieves relevant runbook context using RAG, and returns a GenAI-generated troubleshooting recommendation — instead of an engineer manually grepping logs and Googling stack traces.

## Problem

When a production application fails, engineers have to manually inspect logs, identify the error, determine the likely root cause, and search documentation for a solution. This project automates that first-response loop: **error in → classification + recommended action out**, in under a second.

## Architecture

```
              User/Application
                     │
                     ▼
                FastAPI API
                     │
             ┌───────┴───────┐
             ▼               ▼
           Logs          Error Handler
             │               │
             └───────┬───────┘
                     ▼
             Incident Analyzer
                     │
              ┌──────┴──────┐
              ▼             ▼
          Error Type     Root Cause
              │             │
              └──────┬──────┘
                     ▼
              GenAI Assistant
                     │
                     ▼
       Suggested Troubleshooting Steps
```

- **FastAPI API** — receives incidents via REST, returns structured JSON.
- **Logs** — every request and error is emitted as structured JSON (`src/logging_config.py`), ready to ship to any log aggregator.
- **Error Handler** — a global exception handler catches anything unhandled, logs it with full context, and returns a clean error response instead of leaking a stack trace.
- **Incident Analyzer** — rule-based classifier (`src/error_classifier.py`) maps the raw message + status code to an `error_type`, `probable_cause`, and `severity`. Deterministic and auditable on purpose — see [Error-Handling Strategy](#error-handling-strategy) below.
- **GenAI Assistant** — retrieves relevant runbook excerpts (RAG, `src/rag/`) and asks Claude to turn the classification + context into one concrete recommended action. Falls back to a rule-based recommendation if no API key is configured, so the app degrades gracefully rather than failing.
- **PostgreSQL** — every incident and its full analysis is persisted for history/trend queries (via SQLAlchemy).
- **Dashboard** — a single static HTML page (`src/static/dashboard.html`) reads `/dashboard/summary` for incident counts by severity/service/error-type and a recent-incidents table.

## Technology

| Layer | Choice |
|---|---|
| API framework | FastAPI |
| Database | PostgreSQL + SQLAlchemy ORM |
| Logging | Structured JSON logging (stdlib `logging` + custom formatter) |
| Classification | Rule-based keyword/status-code engine |
| GenAI / RAG | TF-IDF retrieval (scikit-learn) + Anthropic Claude for generation |
| Testing | pytest + FastAPI `TestClient` against an in-memory SQLite DB |
| Containerization | Docker + docker-compose |

## API Endpoints

### `POST /incidents`
Classify a new incident and get a recommendation.

**Input**
```json
{
  "service": "payment-api",
  "error_code": 500,
  "message": "Database connection timeout"
}
```

**Output**
```json
{
  "id": 1,
  "service": "payment-api",
  "error_code": 500,
  "message": "Database connection timeout",
  "error_type": "Database Connectivity",
  "probable_cause": "Connection pool exhaustion",
  "severity": "High",
  "recommended_action": "Check the connection pool for idle-in-transaction sessions and confirm the pool size matches current load.",
  "rag_sources": ["runbook-db-pool", "runbook-db-timeout"],
  "created_at": "2026-08-13T04:45:00Z"
}
```

### `GET /incidents`
List recent incidents. Query params: `limit`, `service`, `severity`.

### `GET /incidents/{id}`
Fetch a single incident by ID.

### `GET /dashboard/summary`
Aggregated counts (by severity, service, error type) + 10 most recent incidents — powers `/dashboard`.

### `GET /health`
Liveness/readiness probe; also checks DB connectivity.

Full interactive docs are auto-generated by FastAPI at **`/docs`** once the app is running.

## Error-Handling Strategy

Two distinct layers, deliberately kept separate:

1. **Runtime error handling** — a global FastAPI exception handler wraps every request. Anything unhandled is logged with full structured context (route, method, stack trace) and the client gets a generic 500 instead of internal details. Expected errors (validation, not-found) return proper 4xx codes via `HTTPException`.
2. **Incident classification** — the *content* of an error (the message + status code an application reports) is matched against an ordered rule set (`src/error_classifier.py`) to assign an `error_type`, `probable_cause`, and `severity`. This is rule-based rather than another LLM call on purpose: classification needs to be fast, deterministic, and auditable, so the same input always lands in the same bucket. The GenAI layer is reserved for the part that benefits from natural-language reasoning — turning a bucket + retrieved runbook context into a concrete next step.

If the GenAI call fails (no API key, network issue, rate limit) the assistant falls back to a deterministic recommendation built from the classification and the top retrieved runbook, so the API never returns a 500 just because the LLM provider is unavailable.

## Testing

```bash
pytest -v
```

Tests run against an in-memory SQLite database (see `tests/conftest.py`), so the suite has no external dependencies and runs in seconds. Covers:
- Classifier rules (`tests/test_error_classifier.py`)
- API endpoints — create/list/get incidents, validation errors, filtering, dashboard summary (`tests/test_incidents.py`)

## Setup & Local Development

```bash
# 1. Clone and enter the project
git clone <your-repo-url>
cd incident-assistant

# 2. Create a virtualenv and install dependencies
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. Configure environment
cp .env.example .env
# edit .env: set DATABASE_URL and ANTHROPIC_API_KEY

# 4. Run PostgreSQL (or point DATABASE_URL at an existing instance)
docker run -d --name incident-db -p 5432:5432 \
  -e POSTGRES_USER=incident_user \
  -e POSTGRES_PASSWORD=incident_pass \
  -e POSTGRES_DB=incident_db \
  postgres:16-alpine

# 5. Run the app
uvicorn src.main:app --reload

# 6. Try it
curl -X POST http://localhost:8000/incidents \
  -H "Content-Type: application/json" \
  -d '{"service":"payment-api","error_code":500,"message":"Database connection timeout"}'
```

Visit **http://localhost:8000/docs** for interactive API docs and **http://localhost:8000/dashboard** for the dashboard.

## Deployment (Docker)

```bash
export ANTHROPIC_API_KEY=your_key_here
docker compose up --build
```

This starts PostgreSQL and the FastAPI app together, wired via `docker-compose.yml`. The app is available at `http://localhost:8000`.

## Possible Extensions

- Add Prometheus metrics / Grafana instead of the static dashboard.
- Ingest logs directly from a log stream (Kafka/CloudWatch) instead of a REST POST.
- Add Alembic migrations instead of `create_all` for schema changes.
